Syntax

Format 1: name the file (ENVIRONMENT DIVISION, INPUT-OUTPUT SECTION, FILE-CONTROL)
SELECT [ OPTIONAL ] file-name
    ASSIGN TO { literal-1 | identifier-1 | DISPLAY | KEYBOARD }
    [ ORGANIZATION IS ] { SEQUENTIAL | LINE SEQUENTIAL | RELATIVE | INDEXED }
    [ ACCESS MODE IS { SEQUENTIAL | RANDOM | DYNAMIC } ]
    [ RELATIVE KEY IS identifier-2 ]
    [ RECORD KEY IS identifier-3 ]
    [ ALTERNATE RECORD KEY IS identifier-4 [ WITH DUPLICATES ] ] ...
    [ FILE STATUS IS identifier-5 ] .

Format 2: describe its records (DATA DIVISION, FILE SECTION)
FD file-name [ IS GLOBAL ]
    [ BLOCK CONTAINS integer-1 [ TO integer-2 ] { RECORDS | CHARACTERS } ]
    [ RECORD CONTAINS integer-3 CHARACTERS ]
    [ RECORD IS VARYING IN SIZE FROM integer-4 TO integer-5 CHARACTERS
          DEPENDING ON identifier-6 ]
    [ LINAGE IS integer-7 LINES [ WITH FOOTING AT integer-8 ]
          [ LINES AT TOP integer-9 ] [ LINES AT BOTTOM integer-10 ] ] .
01 record-name ...
[ 01 record-name-2 ... ] ...

What it does

A COBOL program works with a file in three places. In the ENVIRONMENT DIVISION, a SELECT entry gives the file a name inside the program and says where it is on disk and how it is organized. In the DATA DIVISION, an FD (file description) describes the records. In the PROCEDURE DIVISION, statements open the file, move records in and out, and close it.

A record is one unit of data in the file, such as one customer or one line of a report. The 01 level under the FD is the record area: READ puts the next record there, and WRITE takes the record from there. The program can only see one record of a file at a time.

ASSIGN: which file on disk

ASSIGN TO "pay.dat" names the file on disk. A name with no folder in it means a file in the current folder, the folder the program is running in (in Visual Studio, normally the output folder beside the .exe). You can also give a full path such as "C:\data\pay.dat".

ASSIGN TO a data item (ASSIGN TO LOG-NAME) uses whatever name is in that item when OPEN runs, so one SELECT can open different files at different times. The trailing spaces of the item are ignored.

Before the name is used, the runtime looks for an environment variable that replaces it, the way GnuCOBOL does:

  • For a name with no folder in it, such as pay.dat, it tries the variables DD_pay_dat, dd_pay_dat and pay_dat (dots become underscores). The first one that is set gives the real file name. So set DD_pay_dat=C:\test\pay2.dat redirects the file without changing the program.
  • A part of a path that starts with $, as in "$DATA\pay.dat", is replaced by that variable (here DATA, also tried as DD_DATA and dd_DATA).
  • If COB_FILE_PATH is set, a name that isn't a full path is looked for in that folder instead of the current one.

ASSIGN TO DISPLAY makes a LINE SEQUENTIAL file that writes to the screen (standard output), and ASSIGN TO KEYBOARD one that reads from standard input.

OPTIONAL means the file may be missing: opening it for input then succeeds with status 05 and the first READ is at end (see OPEN).

ACCESS MODE: how the program gets at the records

  • SEQUENTIAL (the default): records are read and written in order, one after the next.
  • RANDOM: each READ or WRITE goes straight to the record whose key you set first: the slot number in the RELATIVE KEY, or the value in the RECORD KEY field.
  • DYNAMIC: both. Use READ ... KEY or a plain READ for direct access, and READ ... NEXT (often after START) to carry on in order from there.

LINE SEQUENTIAL and SEQUENTIAL files are always accessed sequentially.

Keys

RELATIVE KEY names an unsigned numeric item in WORKING-STORAGE (not in the record). With random or dynamic access you put the slot number there before READ, WRITE, REWRITE, DELETE or START; with sequential access the runtime puts the number of each slot it reads or writes there.

RECORD KEY names a field inside the record. Each record must have a different value in it; writing a second record with the same key fails with status 22. An ALTERNATE RECORD KEY is another field you can read by. Add WITH DUPLICATES if several records may share a value (several customers in one city, for example).

FILE STATUS

FILE STATUS IS FS names a two-character item (PIC XX) that the runtime sets after every statement on the file: "00" for success, "10" for end of file, "35" for "file not found", and so on. Always give your files one, and check it. FILE STATUS codes lists them all. Several files may share one status item.

The FD

Each SELECT needs a matching FD with at least one 01 record. Some useful clauses:

  • RECORD CONTAINS 14 CHARACTERS states the record size. It must agree with the 01 level; it adds nothing else.
  • RECORD IS VARYING ... DEPENDING ON LEN makes the records variable in length: before a WRITE you put the length in LEN, and after a READ LEN holds the length of the record just read.
  • BLOCK CONTAINS comes from tape and old mainframe files. It is accepted and has no effect: the file is the same with or without it.
  • LINAGE divides a LINE SEQUENTIAL report file into pages, with margins at the top and bottom and a footing area. See WRITE for an example.

Several 01 levels under one FD are different views of the same record area, like an automatic REDEFINES. A file of heading lines and detail lines can describe both shapes and use whichever fits the record in hand. A READ fills the area; you decide which view to look at.

The life cycle of a file

Every file goes through the same steps:

  1. OPEN it, saying what you will do: INPUT (read), OUTPUT (write a new file), I-O (read and change) or EXTEND (add to the end).
  2. READ, WRITE, REWRITE, DELETE and START as needed.
  3. CLOSE it. A file left open when the program ends is closed for you, with a warning.

SP COBOL notes

SEQUENTIAL, LINE SEQUENTIAL and RELATIVE files are written byte for byte the way GnuCOBOL 3.2 writes them (CR LF line ends, the 4-byte header of variable-length records, the 8-byte header of each relative slot), so programs built with either can share data files. The FILE STATUS values and the AT END / INVALID KEY / END-OF-PAGE conditions are the same too.

Where GnuCOBOL 3.2 has a plain bug in its file handling, SP COBOL does what the code was clearly meant to do, or what the COBOL standard says (see also Differences from GnuCOBOL):

INDEXED files use SP COBOL's own format. GnuCOBOL keeps indexed files through an outside library (Berkeley DB or VBISAM); SP COBOL uses a simple one-file format of its own, pure .NET, with no extra DLLs. The file starts with the header SPCOBIX1 and the key layout, followed by the records in the order they were written. OPEN reads the whole file and builds the key indexes in memory, which is fine for files of thousands of records but not millions. Deleted records leave unused space that isn't reused. The FILE STATUS values are the ones GnuCOBOL reports (02, 21, 22, 23, 39, ...). Indexed files written by SP COBOL and by GnuCOBOL can't be read by each other.

When a file error stops the program (no FILE STATUS and no USE procedure), SP COBOL prints GnuCOBOL's message and then one hint: line for learners, for example:

libcob: error: file does not exist (status = 35) for file NOFILE ('no-such-file.dat')
  hint: Check the name in ASSIGN. The program looked in C:\work\bin. Use OPEN OUTPUT (or SELECT OPTIONAL) to create the file.

Set the environment variable COB_NO_HINTS=1 to leave the hint out. The program ends with exit code 1, as in GnuCOBOL.
