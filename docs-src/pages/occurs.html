title: OCCURS summary: Repeat an item to make a table (an array), with fixed or variable size. keywords: OCCURS TIMES table array subscript index INDEXED BY DEPENDING ON ODO variable length ASCENDING DESCENDING KEY two-dimensional nested ---

Syntax

Format 1: a fixed number of occurrences
OCCURS integer-1 [ TIMES ]
    [ { ASCENDING | DESCENDING } KEY IS data-name-1 ... ] ...
    [ INDEXED BY index-name-1 ... ]

Format 2: a variable number (OCCURS DEPENDING ON)
OCCURS integer-1 TO integer-2 [ TIMES ] DEPENDING ON data-name-2
    [ { ASCENDING | DESCENDING } KEY IS data-name-1 ... ] ...
    [ INDEXED BY index-name-1 ... ]

Referring to an occurrence
data-name ( subscript [ [ , ] subscript ] ... )

What it does

OCCURS makes an item repeat, side by side in memory. The result is a table (other languages call it an array). 05 PRICE PIC 9(3)V99 OCCURS 5 is five prices, one after another. Usually the table is put inside a group (an 01 with the OCCURS item under it), so that the whole table has a name too.

OCCURS can be on an elementary item or on a group. On a group, each occurrence holds the whole group: REGION OCCURS 2 in the example is two copies of a name followed by four sales figures.

Subscripts

You pick one occurrence with a subscript in parentheses after the name. Numbering starts at 1, not 0. A subscript can be a number, a numeric item, an index name, or an item plus or minus a number (ITEM(IX + 1), QTR-SALES(R - 1, Q)). A space before the parenthesis is allowed; inside, a space or comma separates subscripts.

COBOL doesn't check subscripts for you by default, so check your loop limits. The third example and the SP COBOL notes show what happens when a subscript is out of range.

Tables of tables

When an item with OCCURS is inside a group that also has OCCURS, you need one subscript for each level, outermost first. QTR-SALES(2, 4) is the fourth quarter of the second region. This is a two-dimensional table; you can nest further in the same way.

INDEXED BY

INDEXED BY names an index for the table: a special subscript that the compiler keeps in the form that's fastest for that table. You don't declare an index in WORKING-STORAGE. You set and change it with SET (SET IX TO 1, SET IX UP BY 1) or PERFORM VARYING, and SEARCH needs one.

OCCURS DEPENDING ON

Format 2 makes the table's current size come from another item (the ODO object). Room is kept for the maximum, but the group that contains the table is treated as only as long as the current count: a DISPLAY, a MOVE of the whole group, or a WRITE of the record uses just that many occurrences. A variable table must be the last thing in its record.

ASCENDING / DESCENDING KEY

These phrases tell COBOL that the table's entries are kept in order by the named items. They don't sort anything; they are what SEARCH ALL (a binary search) relies on. See SEARCH.

VALUE in tables

A VALUE on an item with OCCURS gives every occurrence that value. See VALUE for starting a table with different values.

Example: a two-dimensional table

Each region holds a 5-byte name and four 4-digit amounts, so a region is 21 bytes and the table 42. The nested PERFORMs fill and total the table with two subscripts. A subscript can be an expression: with R at 1, QTR-SALES(R + 1, 2) is the second quarter of region 2. REGION(1) with one subscript is the whole first group.

Example: DEPENDING ON and INDEXED BY

With ITEM-COUNT at 3, ORDER-REC is 6 + 3 * 4 = 18 bytes long, and a DISPLAY of it stops after the third item. Setting the count to 5 makes it 26 bytes. The loop runs the index IX up to the current count, and SET IX UP BY 1 moves it from 2 to 3.

Example: a subscript past the end

SCORE has 3 occurrences, but the loop runs N up to 4. SCORE (4) would be past the end of SCORE-TABLE, so SP COBOL stops the program there with an error line and a hint, and the exit code is 1. Stock GnuCOBOL prints SCORE 4: followed by whatever two bytes come after the table in memory (here two spaces), then carries on. See the SP COBOL notes.

SP COBOL notes

Deliberate difference from GnuCOBOL 3.2 (see Differences from GnuCOBOL): a subscript or index that reaches past the end of the whole 01 record stops the program with libcob: error: a subscript, index or reference modification is outside its data item and a hint line, exit code 1. Plain GnuCOBOL silently reads or overwrites the bytes after the record; it gives the same error only when the program is compiled with -debug. In SP COBOL each 01 record is its own block of memory, so there are no bytes after it to use. A subscript that stays inside the record (past the table but before the record ends) still reads or changes the items that follow the table, as in GnuCOBOL. Run the program in Visual Studio (F5) to stop on the statement that went out of range.
