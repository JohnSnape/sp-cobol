    Statements

    CALL

    Run another COBOL program as a subprogram, passing it data, and come back.

    Syntax

    CALL { literal-1 | identifier-1 }
    [ USING { [ BY REFERENCE ] identifier-2
            | BY CONTENT { identifier-3 | literal-2 }
            | BY VALUE { identifier-4 | literal-3 } } ... ]
    [ RETURNING identifier-5 ]
    [ ON EXCEPTION imperative-statement-1 ]
    [ NOT ON EXCEPTION imperative-statement-2 ]
[ END-CALL ]

ON OVERFLOW may be written in place of ON EXCEPTION.

In the called program:
PROCEDURE DIVISION [ USING { [ BY REFERENCE ] data-name-1 | BY VALUE data-name-2 } ... ]

    What it does

    CALL runs another program, the called program or subprogram, and continues with the next statement when it finishes (with GOBACK or EXIT PROGRAM). The name is the called program's PROGRAM-ID, written as a literal (CALL "PAYROLL") or held in an alphanumeric data item (CALL PROG-NAME), which lets the program decide at run time what to call.

    Passing data: USING

    The items after USING are the arguments. The called program describes them in its LINKAGE SECTION and lists them, in the same order, in its PROCEDURE DIVISION USING header. They are matched by position, not by name, and should have the same size and PICTURE on both sides.

    PhraseWhat the called program getsCan it change the caller's item?
    BY REFERENCE (the default)the caller's own itemyes
    BY CONTENTa copy of the item or literalno: changes go to the copy
    BY VALUEthe number itself, as a binary integer; the called program declares it BY VALUE too, usually as PIC S9(9) COMP-5no

    A BY phrase applies to the items after it until the next BY.

    Getting a result back: RETURN-CODE and RETURNING

    Every program has a special register, RETURN-CODE. Whatever the called program leaves in it is available to the caller in RETURN-CODE after the CALL. CALL ... RETURNING identifier also stores that value in identifier. To pass back anything else (text, several values), change a BY REFERENCE argument.

    When the program can't be found: ON EXCEPTION

    If no program with that name exists, ON EXCEPTION (or its older spelling ON OVERFLOW) runs instead. NOT ON EXCEPTION runs after a successful call. Without ON EXCEPTION, a missing program stops the run with an error message.

    Inside ON EXCEPTION, end a DISPLAY with END-DISPLAY: ON EXCEPTION DISPLAY "missing" NOT ON EXCEPTION ... attaches the NOT ON EXCEPTION to the DISPLAY, which has exception phrases of its own, not to the CALL. This is standard COBOL, and GnuCOBOL reads it the same way.

    Nested programs and COMMON

    A program can contain other programs, written before its END PROGRAM line. A nested program can be CALLed only by the program that directly contains it, unless it says IS COMMON in its PROGRAM-ID; a COMMON program can also be called by the other programs nested beside it. Items the outer program declares GLOBAL can be used by name in all the programs nested inside it.

    How SP COBOL finds the program

    • It looks for a program with that PROGRAM-ID among everything already loaded: the main program, the other programs in its source file, and the other .cbl files of the project. An exact match comes first, then a match that ignores upper and lower case.
    • Then it looks for NAME.dll beside the program, or in a folder listed in the COB_LIBRARY_PATH environment variable.
    • In a Visual Studio project, every .cbl file is compiled. One becomes the main program: the one named by the CobolMainProgram property if you set it, else Program.cbl, else the only file, else the first file whose PROCEDURE DIVISION has no USING. The others become subprograms the main program can CALL.

    Passing arguments

    The called program, CALLSUB1, is in a source file of its own, shown after the main program.

    The first CALL passes COUNTER by reference, COPY-ME by content and 5 by value. The subprogram adds 20 and 5 to COUNTER, so the caller sees 35. It also sets its copy of COPY-ME to 9999, which the caller never sees. It puts 35 in RETURN-CODE, and RETURNING RESULT picks that up. The second CALL names the program through PROG-NAME and adds 20 + 1 to COUNTER. NOSUCHPROG doesn't exist, so the ON EXCEPTION branch runs. The program sets RETURN-CODE back to 0 at the end, because a main program's RETURN-CODE becomes its exit code.

    Nested programs, COMMON and GLOBAL

    ADD-TEN and LOG-IT are nested inside CALL2. ADD-TEN can call LOG-IT only because LOG-IT is COMMON. LOG-IT reads and changes MESSAGE-TEXT without any USING, because CALL2 declared it GLOBAL.

    A program that isn't there

    Without ON EXCEPTION, the run stops at the CALL with exit code 1. The first message line is the same as GnuCOBOL's; the hint: line is SP COBOL's addition.

    SP COBOL notes

    After the "module not found" message, SP COBOL prints a hint: line saying what to check. GnuCOBOL doesn't. Set the environment variable COB_NO_HINTS=1 to turn hints off.
    Not supported:
    • PROCEDURE DIVISION RETURNING in the called program. GnuCOBOL 3.2 doesn't implement it either. Pass results back through RETURN-CODE or a BY REFERENCE argument.
    • CALL ... RETURNING ADDRESS OF, program pointers (SET pointer TO ENTRY "NAME" and calling through them), and CALL STATIC.
